## 3. MVP 원칙

이 프로젝트는 제한된 기간 안에 핵심 사용자 흐름을 검증하기 위한 MVP다.

다음 원칙을 따른다.

* 핵심 흐름을 방해하지 않는 극단적 상황을 과도하게 설계하지 않는다.
* 필요하지 않은 추상화, 이벤트 시스템, 마이크로서비스를 도입하지 않는다.
* 현재 사용하지 않는 확장 기능을 미리 구현하지 않는다.
* 단순화를 위해 데이터 무결성과 사용자 데이터 격리를 포기하지 않는다.
* AI의 자연어 결과를 신뢰하지 말고 항상 백엔드에서 검증한다.
* 통계와 집계에 사용되는 값은 정규화된 허용 목록으로 제한한다.
* 사용자의 원문은 AI가 교정하거나 재작성하지 않고 별도로 보존한다.
* AI의 판단보다 사용자의 최종 선택을 우선한다.
* 동일 요청이 다시 전송될 가능성을 고려해 저장 API를 가능한 한 멱등적으로 만든다.

# 5. 인증 규칙

## 5.1 사용자 흐름

앱에는 별도의 회원가입 및 로그인 화면이 없다.

프론트엔드는 앱 최초 실행 시 다음 순서를 사용한다.

```text
기존 Supabase 세션 확인
→ 세션이 존재하면 재사용
→ 세션이 없으면 signInAnonymously() 한 번 실행
```

백엔드는 별도의 자체 회원가입, 아이디 로그인, 비밀번호 로그인 API를 구현하지 않는다.

## 5.2 백엔드 인증

모든 사용자 전용 API는 다음 헤더를 요구한다.

```http
Authorization: Bearer <SUPABASE_ACCESS_TOKEN>
```

백엔드는 다음 규칙을 따른다.

* Supabase JWT를 검증한다.
* JWT의 `sub`를 사용자 UUID로 사용한다.
* 요청 body 또는 query에 포함된 사용자 ID를 신뢰하지 않는다.
* 사용자 데이터 소유권은 항상 JWT의 `sub`를 기준으로 검증한다.
* 익명 사용자와 일반 사용자를 서로 다른 내부 ID 체계로 관리하지 않는다.
* 인증되지 않은 요청은 사용자 데이터를 생성하거나 조회할 수 없다.
* 최초 인증 요청에서 `user_profiles`가 없으면 멱등적으로 생성할 수 있다.
* 동시 요청에도 사용자 프로필이 중복 생성되지 않아야 한다.

# 6. 핵심 용어

## 6.1 북극성 지표

사용자가 직접 작성한 삶의 방향, 중요 목표 또는 가치에 대한 원문이다.

예:

```text
가족과 건강을 지키면서 원하는 일을 꾸준히 배우고 싶다.
```

북극성 지표는 사용자의 원문 그대로 저장한다.

홈 화면에서는 상위 성단 이름이 아니라 사용자가 작성한 북극성 지표 원문을 보여준다.

## 6.2 상위 성단

북극성 지표와 하루 기록을 분류하는 16개의 고정 가치 영역이다.

상위 성단은 API, DB, 통계에서 사용하는 canonical value다.

## 6.3 별

하루 기록 하나 또는 완료된 혜성 하나에서 생성되는 기록 단위다.

별은 최종적으로 하나의 주 성단에 속한다.

필요한 경우 보조 성단 후보와 적합도는 분석 근거로 보존할 수 있지만, 기본 집계에는 주 성단 하나만 사용한다.

## 6.4 하위 태그

하루 기록에서 추출되는 구체적인 정보다.

하위 태그의 기본 차원은 다음 5개다.

* 함께한 사람
* 장소
* 활동
* 시간
* 감정

## 6.5 원문 값과 정규화 태그

사람 이름이나 장소 이름 같은 고유명사와 집계용 태그를 구분한다.

예:

```text
원문 값: 민서
정규화 태그: 친구
```

```text
원문 값: 아웃백
정규화 태그: 음식점
```

* 원문 값은 사용자의 기록을 보존하기 위한 값이다.
* 정규화 태그는 검색, 분류, 통계를 위한 허용 목록 값이다.
* 원문 값과 정규화 태그를 하나의 필드에 섞지 않는다.
* 고유명사를 상위 성단이나 정규화 태그 목록에 자동 추가하지 않는다.

문자열을 여러 파일에 반복해서 작성하지 않는다.

하나의 Enum 또는 canonical constants 모듈에서 관리한다.

`가족`은 가족 관계, 돌봄, 가족 활동을 포함한다.

API 계약을 별도로 변경하지 않은 상태에서 canonical value를 `가족·돌봄`으로 변경하지 않는다.

# 8. 상위 성단 판정 기준

## 8.1 가족

가족 구성원과의 관계, 돌봄, 안부, 가족 활동이 기록의 중심일 때 사용한다.

관계·사랑과 충돌하는 경우 상대가 가족 구성원이고 가족 역할이나 돌봄이 핵심이면 `가족`을 우선한다.

## 8.2 관계·사랑

특정 개인과의 친밀감, 애정, 신뢰, 위로, 깊은 대화가 중심일 때 사용한다.

친구 한 명 또는 연인과의 개인적인 경험은 소속감·공동체보다 관계·사랑에 가깝다.

## 8.3 건강

신체적 또는 정신적 건강 유지, 운동, 회복, 수면, 치료가 핵심일 때 사용한다.

헬스장이라는 장소만으로 건강으로 확정하지 않는다.

## 8.4 성장·배움

공부, 독서, 연습, 탐구, 피드백, 새로운 지식 습득이 중심일 때 사용한다.

프로젝트 기록이라도 핵심이 학습이면 커리어·성취보다 성장·배움에 가깝다.

## 8.5 커리어·성취

업무, 프로젝트 결과, 마감, 발표, 취업 준비, 성과 달성이 중심일 때 사용한다.

단순히 학교나 회사에 있었다는 사실만으로 분류하지 않는다.

## 8.6 재정적 안정

저축, 예산, 소비 관리, 수입 관리, 부채 상환 등 재정 관리나 안정이 핵심일 때 사용한다.

비싼 물건을 구매했다는 사실만으로 분류하지 않는다.

## 8.7 자유·독립

사용자가 스스로 결정하고 통제하거나 독립적인 선택을 한 경험이 중심일 때 사용한다.

혼자 있었다는 사실만으로 분류하지 않는다.

## 8.8 창의성·표현

글쓰기, 디자인, 그림, 음악, 개발, 제작 등 아이디어를 표현하거나 결과물을 만든 경험이 중심일 때 사용한다.

모든 개발 활동을 자동으로 커리어·성취에 넣지 않는다. 창작과 표현이 핵심이면 창의성·표현으로 판단한다.

## 8.9 기여·봉사

타인에게 도움을 주거나 지식, 시간, 재능을 나누는 행동이 중심일 때 사용한다.

일반적인 친절과 지속적인 기여 또는 봉사를 구분한다.

## 8.10 영성·신념

기도, 명상, 종교 활동, 철학적 성찰, 삶의 의미나 신념을 돌아보는 경험이 중심일 때 사용한다.

자연에 있었다는 사실만으로 분류하지 않는다.

## 8.11 즐거움·여가

놀이, 취미, 관람, 휴식, 맛있는 음식 등 즐거움 자체가 중심일 때 사용한다.

친구와 식사한 기록에서 친밀한 관계 경험이 핵심이면 관계·사랑을 우선할 수 있다.

## 8.12 모험·도전

처음 하는 경험, 낯선 시도, 두려움을 감수한 행동, 새로운 장소나 활동에 도전한 경험이 중심일 때 사용한다.

단순 여행 기록보다 `처음`, `용기`, `도전`의 의미가 있어야 강하게 판단한다.

## 8.13 소속감·공동체

팀, 동아리, 모임, 스터디 등 집단에 속해 함께한 경험이 중심일 때 사용한다.

친구 한 명과의 깊은 대화는 관계·사랑에 가깝고, 여러 구성원과의 공동 활동은 소속감·공동체에 가깝다.

## 8.14 진정성·자기다움

자신의 가치, 취향, 생각을 솔직하게 표현하거나 스스로를 인정한 경험이 중심일 때 사용한다.

혼자 행동했다는 사실보다 자신의 가치에 맞는 선택을 했다는 의미가 중요하다.

## 8.15 리더십·영향력

사용자가 실제로 사람을 이끌거나 방향을 제시하고, 설득하고, 조율한 행동이 중심일 때 사용한다.

다른 사람과 함께 있었다는 사실만으로 분류하지 않는다.

## 8.16 균형·조화

일과 휴식, 일정, 감정, 생활 패턴을 조정하여 안정과 균형을 회복한 경험이 중심일 때 사용한다.

단순히 편안했다는 감정만으로 확정하지 않는다.

# 9. 하위 태그 분류 체계

하위 태그 후보는 프로젝트에서 미리 정의한다.

Solar는 다음을 함께 보고 판단한다.

* 사용자 원문 전체
* 추출된 원문 값
* 정규화된 하위 태그
* 각 태그가 등장한 문맥
* 문장 내 강조 표현
* 활동과 감정의 결합
* 사람 수와 관계 형태
* 시간 표현

백엔드는 다음을 담당한다.

* 허용된 하위 태그인지 검증
* 원문 값과 정규화 태그를 분리해 저장
* 상위 성단이 허용 목록인지 검증
* AI 결과 JSON 구조 검증
* 사용자의 최종 수정 결과 저장

하위 태그 하나를 상위 성단 하나에 고정 연결하지 않는다.

잘못된 예:

```python
TAG_TO_CATEGORY = {
    "편안함": "균형·조화",
    "친구": "관계·사랑",
}
```

허용되는 방식:

```python
TAG_CATEGORY_HINTS = {
    "편안함": [
        "관계·사랑",
        "균형·조화",
        "즐거움·여가",
        "진정성·자기다움",
    ],
    "친구": [
        "관계·사랑",
        "소속감·공동체",
        "즐거움·여가",
        "모험·도전",
    ],
    "운동": [
        "건강",
        "모험·도전",
        "성장·배움",
    ],
}
```

이 목록은 후보를 좁히는 힌트일 뿐 최종 상위 성단을 결정하는 고정 매핑이 아니다.

# 11. 장소와 시간의 역할

장소와 시간은 원칙적으로 상위 성단을 단독 결정하지 않는다.

활동, 사람, 감정, 원문 전체의 의미를 보조하는 증거로만 사용한다.

## 11.1 장소별 후보 힌트

| 장소 태그  | 강화 가능한 후보 성단        |
| ------ | ------------------- |
| 집      | 가족, 균형·조화, 즐거움·여가   |
| 학교·도서관 | 성장·배움, 커리어·성취       |
| 회사·연구실 | 커리어·성취, 리더십·영향력     |
| 헬스장·공원 | 건강                  |
| 카페·음식점 | 관계·사랑, 즐거움·여가       |
| 종교 시설  | 영성·신념               |
| 봉사 기관  | 기여·봉사               |
| 자연·여행지 | 모험·도전, 균형·조화, 영성·신념 |

## 11.2 시간 표현별 후보 힌트

| 시간 표현 | 강화 가능한 후보 성단        |
| ----- | ------------------- |
| 오랜만에  | 가족, 관계·사랑, 소속감·공동체  |
| 처음으로  | 모험·도전, 성장·배움        |
| 꾸준히   | 건강, 성장·배움, 균형·조화    |
| 마감 전에 | 커리어·성취              |
| 주말에   | 즐거움·여가 가능성          |
| 혼자    | 자유·독립, 진정성·자기다움 가능성 |

다음 표현 자체에는 상위 성단 의미를 부여하지 않는다.

```text
아침
오후
저녁
밤
몇 시
```

# 12. 문맥 기반 성단 판정

다음 기록을 예로 든다.

```text
민서랑 아웃백에서 치킨 먹음.
오랜만에 편하게 얘기함.
```

추출 가능 정보:

```text
함께한 사람 원문 값: 민서
함께한 사람 정규화 태그: 친구

장소 원문 값: 아웃백
장소 정규화 태그: 음식점

활동: 함께 식사, 대화
시간: 오랜만에
감정: 편안함
```

단순 고정 매핑을 사용하면 다음처럼 흩어질 수 있다.

```text
친구 → 관계·사랑
함께 식사 → 즐거움·여가
편안함 → 균형·조화
```

그러나 기록 전체의 중심은 음식이 아니라 오랜만에 친구와 편안한 대화를 나눈 관계 경험이다.

권장 결과:

```json
{
  "primary_category": "관계·사랑",
  "secondary_categories": [
    {
      "category": "소속감·공동체",
      "score": 0.61
    },
    {
      "category": "즐거움·여가",
      "score": 0.42
    }
  ],
  "evidence": [
    "민서랑",
    "오랜만에",
    "편하게 얘기함"
  ]
}
```

최종 별 집계에는 `primary_category`만 사용한다.

보조 성단은 설명과 분석 근거로만 활용한다.

# 13. 하루 기록 흐름

하루 기록은 다음 순서를 따른다.

```text
사용자가 자유롭게 하루를 작성
→ Solar가 5개 차원 정보 추출
→ 부족한 차원 판단
→ 백엔드가 고정 질문 유형에 맞는 질문 제공
→ 사용자 추가 응답
→ 추출 결과와 후보 태그 제시
→ 사용자 수정 및 확인
→ 성단 순위 계산
→ 사용자 최종 저장 승인
→ 별 생성
```

## 13.1 다섯 가지 차원

```text
함께한 사람
장소
활동
시간
감정
```

모든 기록에 다섯 차원이 반드시 하나씩 존재해야 하는 것은 아니다.

예를 들어 혼자 한 활동이라면 `함께한 사람`은 `나 자신` 또는 명시적인 없음으로 처리할 수 있다.

AI가 정보를 만들기 위해 존재하지 않는 사람, 장소, 감정을 추측하면 안 된다.

## 13.2 정보 충분성 판단

Solar는 각 차원에 대해 다음 상태를 반환한다.

```text
PRESENT
MISSING
AMBIGUOUS
NOT_APPLICABLE
```

* `PRESENT`: 원문에서 충분히 확인 가능
* `MISSING`: 기록에 필요한 정보가 없음
* `AMBIGUOUS`: 여러 해석이 가능해 사용자 확인 필요
* `NOT_APPLICABLE`: 해당 기록에 적용되지 않음

모든 누락 항목을 무조건 질문하지 않는다.

별의 성단 판단에 실질적으로 필요한 정보가 부족할 때만 질문한다.

---

# 14. 허용된 질문 유형

AI가 사용자에게 보낼 질문 문장을 자유롭게 생성하지 않는다.

AI는 필요한 질문 유형만 반환한다.

허용된 질문 유형:

```text
PERSON
PLACE
ACTIVITY
TIME
EMOTION
```

백엔드 또는 프론트는 질문 유형을 고정 문구에 매핑한다.

권장 기본 질문:

```text
PERSON: 오늘 누구와 함께했나요?
PLACE: 어디에서 있었나요?
ACTIVITY: 무엇을 했나요?
TIME: 언제였거나 어떤 시간적 맥락이 있었나요?
EMOTION: 그때 어떤 감정이 들었나요?
```

질문 프리셋은 별도 canonical constants로 관리한다.

AI가 반환한 임의 질문 문장을 그대로 사용자에게 보여주지 않는다.

---

# 15. 사용자 수정 방식

사용자는 AI 추출 결과를 최종 확정한다.

사용자가 최종적으로 맡는 결정:

* 추출된 하위 정보 확인
* 잘못 추출된 값 수정
* 모호한 후보 중 적합한 값 선택
* 감정 태그 확인
* 최종 기록 저장 승인
* 주 성단이 틀린 경우 수정

정규화 태그는 허용된 목록 중에서 선택한다.

모호한 경우 AI는 한 차원당 최대 3개의 정규화 후보를 제시할 수 있다.

사람 이름, 장소 이름 같은 원문 고유명사는 별도의 원문 값으로 보존한다.

예:

```json
{
  "dimension": "PERSON",
  "raw_value": "민서",
  "normalized_candidates": [
    "친구",
    "가까운 사람"
  ]
}
```

사용자가 선택하거나 수정한 최종 결과가 AI 결과보다 우선한다.

# 17. AI 출력 공통 규칙

Solar 호출은 항상 구조화된 JSON 출력을 요구한다.

다음 규칙을 공통 적용한다.

* Markdown을 출력하지 않는다.
* 코드 블록을 출력하지 않는다.
* JSON 앞뒤 설명을 출력하지 않는다.
* 허용 목록 밖의 상위 성단을 출력하지 않는다.
* 존재하지 않는 사용자 사실을 만들지 않는다.
* 근거 문구는 원문에서 직접 찾을 수 있어야 한다.
* 내부 추론 과정을 장문으로 출력하지 않는다.
* 결과 설명은 짧고 사용자에게 보여줄 수 있는 문장으로 제한한다.
* 적합도는 0 이상 1 이하 값으로 반환한다.
* 동일 목록에서 같은 태그를 중복 반환하지 않는다.

백엔드는 모델 응답을 Pydantic schema 등으로 검증한다.

검증 실패 결과를 DB에 저장하지 않는다.

# 18. 북극성 분석 JSON 계약

권장 구조:

```json
{
  "candidates": [
    {
      "category": "가족",
      "score": 0.94,
      "recommended": true,
      "evidence": [
        "가족과",
        "지키면서"
      ],
      "reason": "가족 관계와 돌봄을 중요하게 표현함"
    }
  ]
}
```

검증 규칙:

* 후보는 정확히 7개
* 모든 후보는 서로 달라야 함
* 허용된 16개 성단만 사용
* 적합도 내림차순
* 추천 후보는 최소 1개, 최대 3개
* 근거는 원문 일부
* 사용자는 7개 중 1개 이상 선택 가능

북극성 원문과 사용자가 선택한 성단을 함께 저장한다.

# 21. 홈 화면 규칙

홈 화면에서는 다음을 제공한다.

* 사용자가 작성한 북극성 지표 원문
* 성단별 별
* 오늘의 별 기록하기
* 랜덤하게 등장하는 혜성

홈 화면에서 상위 성단 이름을 북극성 지표 대신 표시하지 않는다.

북극성 지표 영역에는 사용자가 작성한 글을 보여준다.

# 22. 혜성 추천 규칙

혜성은 사용자의 북극성 성단 중 실제 별이 상대적으로 부족한 영역을 위한 작은 행동 추천이다.

처리 순서:

```text
사용자의 활성 북극성 성단 조회
→ 성단별 별 개수 집계
→ 부족한 성단 선정
→ Solar에 해당 성단과 사용자 맥락 전달
→ 구체적인 할 일 추천
→ 사용자 수락 또는 거절
```

부족한 성단의 선정은 AI가 아니라 백엔드가 계산한다.

기본적으로 다음 요소를 고려한다.

* 사용자가 선택한 북극성 성단
* 성단별 별 개수
* 전체 별 개수
* 최근 기록 기간
* 최근 혜성 추천 및 거절 이력
* 이미 진행 중인 혜성

Solar는 선정된 부족 성단을 달성할 수 있는 구체적인 행동만 추천한다.

추천은 다음 조건을 만족해야 한다.

* 한 번의 행동으로 이해 가능
* 지나치게 거창하지 않음
* 사용자가 직접 수행 가능
* 불법, 위험, 의료적 판단을 요구하지 않음
* 비용이나 시간이 과도하게 들지 않음
* 추천 대상 성단이 명시됨

권장 출력:

```json
{
  "target_category": "건강",
  "title": "저녁에 20분 산책하기",
  "description": "오늘 저녁 가까운 곳을 20분 정도 걸어보세요.",
  "reason": "최근 기록에서 건강 성단의 별이 상대적으로 적기 때문입니다.",
  "estimated_minutes": 20
}
```

사용자가 수락하면 혜성 관측소의 할 일로 저장한다.

사용자가 거절하면 거절 이력을 저장하여 같은 추천을 반복하지 않도록 한다.

---

# 23. 혜성 관측소 규칙

혜성 관측소에는 다음 할 일이 들어간다.

* AI 추천을 사용자가 수락한 혜성
* 사용자가 능동적으로 추가한 혜성

혜성 상태는 최소한 다음을 구분한다.

```text
PENDING
COMPLETED
REJECTED
CANCELLED
```

완료된 혜성은 해당 혜성의 목표 성단에 별 하나를 생성한다.

혜성 완료와 별 생성은 하나의 트랜잭션으로 처리한다.

같은 혜성을 반복 완료해 별이 중복 생성되지 않도록 한다.

---

# 24. 은하 개요 규칙

은하 개요는 백엔드가 계산한 통계와 Solar의 짧은 해석으로 구성한다.

필수 정보:

* 현재 연도
* 현재 계절
* 총 별 개수
* 생성된 별자리 개수
* 관측 기간
* 활성 성단 개수
* 성단별 별 개수
* 전체 별 대비 성단별 비율
* AI 세 줄 분석

비율 계산은 백엔드에서 수행한다.

```text
성단 비율 = 해당 성단의 별 개수 / 전체 별 개수
```

전체 별이 0개인 경우 0으로 나누지 않는다.

AI에게 수치 계산을 맡기지 않는다.

AI에는 백엔드가 계산한 확정 수치만 전달한다.

---

# 25. 개요 세 줄 요약 규칙

Solar는 정확히 세 개의 짧은 문장 또는 세 줄 배열을 반환한다.

예:

```json
{
  "lines": [
    "북극성은 가족과 균형을 가리키고 있습니다.",
    "하지만 이번 기간의 별은 성장·배움에 더 많이 모였습니다.",
    "다음 기록에서는 가족과 함께한 순간도 관측해 볼 수 있습니다."
  ]
}
```

다음 내용을 만들면 안 된다.

* 실제 수치와 다른 주장
* 존재하지 않는 기록
* 사용자를 평가하거나 비난하는 문장
* 의료 또는 심리 진단
* 과도한 단정
* 네 줄 이상의 장문

---

# 26. 계절별 은하 분석 리포트

리포트는 계절을 기준으로 생성한다.

프로젝트에서 사용하는 계절 기준은 하나로 고정한다.

예시:

```text
봄: 3월~5월
여름: 6월~8월
가을: 9월~11월
겨울: 12월~2월
```

실제 기준은 최신 API 또는 화면 명세를 확인한다.

리포트에 포함할 수 있는 정보:

* 북극성과 활성 성단 소개
* 성단별 별 개수
* 성단별 비율
* 가장 큰 성단
* 가장 작은 성단
* 전체 태그에서 자주 등장한 사람
* 자주 등장한 장소
* 자주 등장한 활동
* 자주 등장한 시간 표현
* 자주 등장한 감정
* 월별 가장 큰 성단 변화
* 미관측 영역
* 종합 소감 질문

월별 집계와 빈도 계산은 백엔드에서 한다.

Solar는 계산된 통계를 해석하고 문장으로 표현한다.

---

# 27. 계절 리포트 마무리 질문

기본 템플릿:

```text
{가장 큰 성단}을/를 크게 신경 쓴 {연도}년 {계절}은/는 어떠셨나요?
```

한국어 조사는 가능한 경우 백엔드에서 자연스럽게 처리하거나 문장을 조사 의존성이 낮은 형태로 바꾼다.

권장 대체 문구:

```text
{연도}년 {계절}, 가장 많은 별이 모인 성단은 {가장 큰 성단}이었습니다. 이 계절은 사용자에게 어떤 시간이었나요?
```

사용자의 답변은 리포트 종합 소감으로 별도 저장한다.

---

# 28. 데이터 저장 원칙

* 사용자 원문을 보존한다.
* AI 정규화 결과를 별도 저장한다.
* 사용자 최종 수정값을 별도 식별할 수 있어야 한다.
* AI 모델명 또는 분석 버전을 저장한다.
* 생성 시각과 수정 시각을 저장한다.
* 시간은 서버에서 UTC로 저장한다.
* API에서 필요한 경우 ISO 8601 형식으로 반환한다.
* 사용자 데이터 조회에는 반드시 사용자 UUID 조건을 포함한다.
* 집계 대상에서 삭제된 기록 또는 취소된 혜성을 제외한다.
* 동일한 완료 이벤트로 별이 두 번 생성되지 않도록 유일 제약 또는 멱등 키를 사용한다.

---

# 29. API 설계 원칙

* 기존 API 명세를 우선한다.
* 리소스 이름을 일관되게 사용한다.
* 사용자 UUID를 요청 body에 받지 않는다.
* AI 분석과 최종 저장을 분리한다.
* 분석 결과에는 소유자와 만료 시간을 둔다.
* 사용자가 최종 승인하기 전 분석 결과를 확정 기록으로 처리하지 않는다.
* 입력 문자열 길이를 제한한다.
* 빈 문자열과 공백 문자열을 거부한다.
* Enum 값은 API schema에서 명시한다.
* 클라이언트가 허용 목록 밖의 태그를 제출하면 4xx 오류로 거부한다.
* AI 연동 장애와 사용자 입력 오류를 구분한다.

---

# 30. 오류 처리 원칙

사용자에게 내부 예외, SQL, 프롬프트, API Key를 노출하지 않는다.

구분해야 하는 오류:

* 인증 실패
* 권한 없음
* 존재하지 않는 리소스
* 잘못된 입력
* 만료된 분석 결과
* 중복 요청
* Solar timeout
* Solar 비정상 응답
* Solar JSON schema 불일치
* DB 오류

로그에는 디버깅에 필요한 correlation ID를 남길 수 있다.

Access Token, API Key, 전체 사용자 원문은 기본 로그에 남기지 않는다.

---

# 31. Solar 프롬프트 관리

* Solar 시스템 프롬프트를 라우터 함수 안에 직접 길게 작성하지 않는다.
* 기능별 프롬프트를 분리한다.
* 프롬프트 버전을 코드로 관리한다.
* 출력 JSON schema를 프롬프트와 코드 양쪽에서 명시한다.
* 모델명과 API endpoint는 환경변수 또는 설정 모듈에서 관리한다.
* timeout을 설정한다.
* 무한 재시도하지 않는다.
* 형식 오류 재시도는 최대 한 번을 기본으로 한다.
* 테스트에서는 실제 Solar API를 호출하지 않는다.

권장 기능 분리:

```text
north_star_analysis
daily_record_extraction
constellation_classification
galaxy_overview_summary
comet_recommendation
seasonal_report
```

# 32. 테스트 원칙

새 기능에는 최소한 다음 종류의 테스트를 포함한다.

## 단위 테스트

* Enum 검증
* 태그 allowlist 검증
* 중복 제거 또는 중복 거부
* 적합도 범위
* 성단 비율 계산
* 부족한 성단 선정
* 계절 계산
* 한국어 마무리 문구
* Solar JSON 파싱

## API 테스트

* 인증 헤더 없음
* 유효하지 않은 JWT
* 다른 사용자의 데이터 접근
* 정상 생성
* 정상 조회
* 잘못된 태그 제출
* 만료된 분석 결과
* 같은 요청 반복
* AI 장애
* DB rollback

## 통합 테스트

* 북극성 분석부터 최종 저장
* 하루 기록 분석부터 별 생성
* 혜성 수락부터 완료 및 별 생성
* 계절 리포트 집계

실제로 실행하지 않은 테스트를 통과했다고 보고하지 않는다.

---

# 33. 금지 사항

다음을 하지 않는다.

* 상위 성단을 AI가 임의 생성
* 하위 태그 하나를 상위 성단 하나에 고정 매핑
* 장소만 보고 성단 확정
* 시간대만 보고 성단 확정
* AI가 계산한 비율을 그대로 저장
* 사용자 UUID를 body에서 받아 소유권 판단
* 사용자 원문을 AI 요약문으로 덮어쓰기
* AI 결과를 검증 없이 DB에 저장
* 사용자 승인 전에 별 생성
* 완료된 혜성을 반복 완료해 별 중복 생성
* 원본 upstream 저장소에 직접 커밋 또는 push
* PR 자동 merge
* 기존 migration 기록 삭제
* 작업과 무관한 대규모 리팩터링
* MVP에 필요하지 않은 범용 AI 에이전트 시스템 도입
